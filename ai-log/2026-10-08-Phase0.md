● What this repo does: Nothing runs yet. There is no source code, no build
  config, no dependencies and no tests. The repo holds the brief (CLAUDE.md),
  positioning and Phase 0 decision docs, a worklog and one AI-log export. So I

  Must fix

  1. Anyone can make us send a phishing e-mail (docs/decisions.md:146, :154,
     :162)
     - What this is: The form sends hidden fields (tickers, amounts, UTM tags)
       to /api/lead. The server then e-mails a plan built from those fields to
       whatever address was typed in.
     - Problem: Those fields come from the browser, so an attacker can put
       anything in them. If they post email=victim@x.cz and tickers=<a
       href="evil">Váš účet je zablokován</a>, our real sender delivers that
       link to a stranger. The /plan?… page has the same hole, because it builds
       the page from URL parameters.
     - Fix: Add one rule to the plan. The server and /plan accept only tickers
       that exist in data/etfs.json, clamp numbers to fixed ranges, and drop
       everything else. Text gets inserted as plain text, never as HTML. UTM
       values are stored but never put into the e-mail.
     - If we skip it: Our domain becomes a phishing relay. Brevo (the e-mail
       service) blocks the account and real leads stop getting their plan.
  2. Nothing stops the form from being sent over and over
     (docs/decisions.md:262)
     - What this is: Each form submission sends one e-mail through Brevo's free
       plan, which has a daily sending limit (the exact number is still to
       verify).
     - Problem: A script can call /api/lead hundreds of times with random
       addresses. That uses up the day's limit, and later visitors who really
       came from the ad get no e-mail. A honeypot (a hidden field only bots fill
       in) does not stop a script written for this one form.
     - Fix: In the function, refuse a repeat send to the same address within 24
       hours, and cap requests per IP address per hour. A few lines; no new
       service needed.
     - If we skip it: One bored person stops all lead delivery for the day while
       we pay for the ads.

  Should fix

  3. A returning visitor gets an error (docs/decisions.md:99, :154)
     - What this is: The plan has two forms on the page (inline and a sticky
       bottom bar), plus a third at the end.
     - Problem: Someone who submits twice, or comes back tomorrow, already
       exists as a contact in Brevo. If the handler treats Brevo's "contact
       already exists" answer as a failure, the visitor sees an error and
       lead_submitted never fires, even though we have their address.
     - Fix: Write in the plan that an existing contact counts as success: update
       its fields and resend the plan, subject to finding 2's 24-hour limit.
     - If we skip it: Real leads see an error, and our funnel shows fewer
       conversions than really happened.
  4. The honeypot can catch real people (docs/decisions.md:146)
     - What this is: A hidden field that only bots fill in. The server ignores
       any submission where it is filled.
     - Problem: Phone browsers autofill fields with names like name or phone,
       even hidden ones. That visitor's lead is silently dropped and they get no
       e-mail.
     - Fix: Give the field a meaningless name with autocomplete="off" and
       tabindex="-1". Pretend to succeed for bots, but log the drop so we can
       count false positives.
     - If we skip it: A small share of real leads vanish and nobody notices.
  5. Two documents disagree about consent (CLAUDE.md:64 vs
     docs/decisions.md:141)

     - Fix: Change the CLAUDE.md line to "e-mail only + optional, unticked

     - If we skip it: We build the wrong form, or the reviewer sees two
       conflicting rules.

  6. Unknown ad tags are not handled (docs/decisions.md:122-124)
